# Changelog (usap)

## Unreleased
### Security
* The local server now refuses requests that carry a foreign `Origin`, and (when bound to loopback) a non-loopback `Host`. Wildcard CORS headers are removed. The built-in UI is same-origin and is unaffected.
* Static file serving is confined to `app/dist/`.
* Outbound requests (web search, page fetching, model and engine downloads, Hugging Face lookups) can only reach public internet addresses. Each redirect is validated and the number of redirects is limited. The address checked is the address connected to. Search and normal downloads are unaffected (Step 9.3).
* Downloads are verified (Step 9.4). Engines, the portable Node.js and catalog models must match SHA-256 digests and sizes pinned in `scripts/config/download-digests.txt`; Node.js digests come from its GPG-signed checksum list. Other downloads are labelled `source-checksum` (transfer integrity only) or `unverified`. Files stream to a temporary file and replace the old one atomically only after verification, so a failed, interrupted or tampered download keeps the last-known-good file. Engine installs are staged, checked for the right CPU architecture and swapped in whole. Interrupted transfers are retried from the start, never resumed. See `docs/security/DOWNLOAD_INTEGRITY.md`.
* The in-app model download no longer builds a shell command for unzipping (S-8).
* **Sign-in for network sharing** (Step 9.5, S-7, #25). When the server listens beyond loopback (`UAIS_HOST`), every request from another device needs the access token, either through a server-rendered sign-in page (an `HttpOnly`, `SameSite=Strict` session cookie) or as `Authorization: Bearer`. The token is random (256 bits) and kept in `app/config/lan-access-token`; it is never logged or accepted in a URL. `node scripts/server/lan-auth.cjs rotate` signs everyone out, and `revoke` refuses all network access; both apply without a restart. Failed attempts are rate limited per client. The studio no longer forwards cookies or `Authorization` to its local image engine. The token file is restricted to the current user (mode 0600, or a Windows ACL without inherited, `Users` or `Everyone` entries), with a startup warning on drives without permissions (FAT/exFAT). Requests carrying proxy headers never get the local exemption, and throttling ignores forwarding headers. See `docs/security/LAN_ACCESS.md`.
* **Web context hardening (#42).** Text from web pages enters chat as quoted, size-capped data between per-request markers that a page can't predict. Chat-template control tokens (ChatML, Llama 3, Gemma, Mistral) are removed from it, so a page can't open a new system or assistant turn. Citations `[n]` and the UI's source list are unchanged. This reduces, but doesn't remove, the risk that a model follows instructions written in a page.
* **History marking (P3, off by default; owner approval needed to turn it on).** With `historyWeb` on (`app/config/prompt-boundary.json` `{ "historyWeb": "on" }`, or `USAP_PROMPT_HISTORY_WEB=on`, read per request), earlier assistant answers are sent to the model with chat-template control tokens removed, and answers that cited web sources also have marker brackets defused. Roles, order, other text (code included) and saved conversation files don't change. It doesn't remove plain-language instructions an answer may repeat.
* **Document records (P4-1, off by default; owner approval needed to turn it on).** `POST /api/llm/chat` accepts structured `attachments: [{ type: "document", name, text }]` on user messages. The server validates them (user messages only, at most 8 per message and 64 per request, only `type`/`name`/`text`, one-line names up to 200 characters, string text; otherwise `400 INVALID_ATTACHMENTS`) and caps document text at 120,000 characters per message and 240,000 per request with a visible note. A top-level `attachments` field is refused. With `documents` off (default), records become the chat screen's current inline text, byte for byte. With `documents: "mark"` (`app/config/prompt-boundary.json` or `USAP_PROMPT_DOCUMENTS=mark`, read per request), each document is sent between per-request random markers, quoted, with chat-template control tokens and marker brackets neutralized, and document text is kept out of web-search queries. `[Attached File: …]` text in a message is never treated as a document. Requests without records, the chat screen and saved conversations are unchanged. It doesn't stop plain-language instructions in a document.
* Web text now also has DeepSeek full-width tokens, Mistral control tokens (`[SYSTEM_PROMPT]`, `[AVAILABLE_TOOLS]`, `[TOOL_CALLS]`, `[TOOL_RESULTS]`, `[TOOL_CONTENT]`) and Qwen/Hermes `<tool_call>`/`<tool_response>` tags removed, in addition to the #42 families. Ordinary text that only resembles them is kept. Found by the P1 adversarial tests.
* **Web search query privacy (#43).** The automatic query planner now sees only the user's own last 3 messages, never assistant answers (which can repeat untrusted web content) or system prompts. A planned query that copies words from elsewhere in the conversation is refused before it reaches the search provider, and the latest user message is searched instead. The refused query is not logged. Compatibility: a follow-up that refers only to something the assistant said ("what does it cost?") is searched with the user's message as typed.
* `GET /api/web-search/config` reports `cachePath` relative to the studio folder (`app/cache/search`, or `~/…` outside it) instead of the absolute host path (#44). Same field, same type.
* **No absolute host paths in status responses (#52).** `GET /api/health`, `/api/diagnostics`, `/api/backend-options`, `/api/llm/status`, `/api/llm/backends`, `/api/llm/stats`, `/api/speech/status` and `/api/tts/status` now return paths inside the studio folder as studio-relative (`app/…`, the folder itself as `.`) and paths in the home folder as `~/…`, for every client including localhost. This covers engine, runtime and interpreter (`python`) paths, and paths quoted inside status messages (`error`, `reason`, `hint`). Values in `settings` are left as they are. System locations (e.g. `/usr/bin`) are unchanged. Field names and types are unchanged, the interface doesn't display these fields, and the server still uses absolute paths internally. Relative values resolve against the studio folder, so local troubleshooting keeps the same information without the user name.
* **Web search snippets are back (#45).** The result parser now reads each result on its own, so snippets are kept on the real results page. They were dropped whenever other markup sat between title and snippet. Order, URLs, de-duplication and limits are unchanged. Sponsored results are still included; see #50.
* **Sponsored search results are skipped (#50).** Results marked as ads on the results page (`result--ad`, an ad badge) and links that go through an ad-click redirect (`duckduckgo.com/y.js`, `bing.com/aclick`, `googleadservices.com/pagead/aclk`, `doubleclick.net`) are no longer used as sources, so the studio never opens them (which could count as an ad click) and their text doesn't reach the model. The result limit counts real results only, so a search still returns up to the same number of sources. Unmarked ads can still appear.
* JSON API routes require `Content-Type: application/json` (S-9). Other declared types and untyped bodies get `415`; a `POST` without a body still works.
### Reliability
* **Whisper threads never exceed the logical CPUs (on by default).** Each transcription passes whisper.cpp `min(requested, logical CPUs)` threads (`os.cpus().length`; an unknown, zero or invalid count changes nothing). A request at or below the CPU count is unchanged and no count is ever raised. It runs before the optional Step 9.9e budget. Saved speech settings keep the user's value; only that job's `-t` changes. `GET /api/resources` gains one additive `whisperThreadCap` object (requested and used counts, numbers only); the transcription response and `limits` are unchanged. The text and image engines, Kokoro and the macOS Intel image cap are untouched; no engine restarts. Rollback: `USAP_WHISPER_THREAD_CAP=off`, `"whisperThreadCap": "off"` in `app/config/scheduler.json`, or `USAP_SCHEDULER=off` restore the previous behaviour exactly. Measured on 3–4-vCPU CI runners only (STEP9_9E_THREADS.md §8): not a promised speed-up elsewhere.
* **Transcription thread budget (Step 9.9e, whisper only, off by default; owner approval needed to turn it on).** With `USAP_THREADS=on` (or `"threads": "on"` in `app/config/scheduler.json`), a transcription that starts while a chat is running, an image is generating or a voice job is running gets `max(1, min(requested, 2, logical CPUs − 1))` whisper.cpp threads instead of the requested count, which reduces CPU oversubscription. Alone, the requested count is used as before. The text and image engines keep their thread counts and are never restarted, Kokoro is unchanged, and nothing is refused or delayed. Busy is read from server state, never from the request; anything unknown keeps the requested count. `GET /api/resources` shows `limits.threads` and, when on, the last decision. Off (the default, or `USAP_SCHEDULER=off`) is the previous behaviour exactly. The image proxy now counts generation requests in flight (read-only).
* **Warn-only memory check before a model loads (Step 9.9d).** Just before the text engine (including automatic restarts) or the image engine starts with a model, the studio compares what the model is estimated to need (measured file sizes, plus for text models the KV cache at the chosen context from the GGUF header and a 256 MiB allowance) with the memory the system reports as available. The result is `likely-fits`, `tight`, `may-not-fit` or `unknown`, with measured values and estimates labelled separately. It appears as an additive `memoryCheck` field in the `POST /api/llm/start` and `POST /api/restart-backend` responses, under `memory.checks` in `GET /api/resources` (`limits.memoryCheck: "warn"`), and as one `[memory]` log line. It is advisory only: no load or chat is refused, delayed or changed, and no setting, queue decision or thread count changes. Unknown or implausible memory readings, missing model metadata, discrete GPU offload and image working memory give `unknown`, never `likely-fits`. Results contain no paths, file or model names. `USAP_MEMORY_CHECK=off` (or `"memoryCheck": "off"` in `app/config/scheduler.json`, or `USAP_SCHEDULER=off`) restores the previous responses exactly. No UI change.
* **Cut-off engine error responses are answered (#90).** When the text engine answered a streaming chat with an error status and then lost the connection before the error body was complete (engine crash, reset), the client never got an answer, and with the chat queue on its slot stayed held. The chat now answers `500 ENGINE_CONNECTION_ERROR` with the generic message (the partial engine text is never forwarded), exactly once, without retrying, and the queue slot is released. A complete engine error response is answered as before. An engine connection that stays open without sending anything is a different case and is not covered: it needs a timeout for a running request (Step 9.9f).
* **Chat engine connections (found by the real-model chat-queue checks).** A streaming chat that started right after another one could reuse a kept-alive connection that llama-server had just closed, and failed with `500 socket hang up`; it is now sent once more on a new connection, only when the connection had carried an earlier request, failed within 2 s with nothing back from the engine, nothing had been sent to the client and the client is still there (never more than once, and web search doesn't run again). Other engine connection errors answer `500 ENGINE_CONNECTION_ERROR` with a generic message instead of Node's, which could name the engine's local address. A chat that reaches an engine that has just stopped or crashed now answers `409 ENGINE_NOT_READY` instead of a raw `500` naming the engine's local address. Other errors and all successful responses are unchanged.
* **Engine supervision** (Step 9.6, #29). Every chat, image, speech and voice engine runs under a small guard process (`scripts/server/engine-guard.cjs`) that stops it when the studio server goes away for any reason. On Linux and macOS, a crash or `SIGKILL` used to leave the engine running with its memory and port. Windows already ended engines with the server, through Node's job object. Stops are polite first, then forced after 3 s (`USAP_ENGINE_STOP_GRACE_MS`), and wait for the port to be free. Exit codes and crash signals (e.g. Metal `SIGABRT`) still reach the server.
* A text engine that crashes after loading is restarted with the same settings after 1 s, 2 s and 4 s, at most 3 times in 10 minutes (`USAP_ENGINE_AUTO_RESTART=0` turns this off). After that, chat explains what happened. An engine that ran out of memory is never restarted (allocation errors, Windows `STATUS_NO_MEMORY`, or less free RAM than the model needs), and neither is one stopped on purpose.
* Stopping the text engine during a model load cancels it at once, instead of waiting for the load to finish, and no fallback backend is tried afterwards. `USAP_LLM_READY_TIMEOUT_MS` overrides the load timeout.
* An unexpected image-engine crash signal is reported as a clear error.
* An engine file that exists but can't be started (not executable, for example after copying to a FAT32 or exFAT drive, or a folder in its place) no longer stops the whole server (#68). The text, image and speech engines now report it as a failed start with a short explanation and no paths ("Could not start the text engine (llama.cpp) (EACCES). …"); the text engine then tries the next backend or profile as before, nothing is left running, and the next start works once the engine is repaired. The server log keeps the full details.
* Non-streaming chat (`POST /api/llm/chat` with `stream: false`) now reports the text engine's own error message and status, like streaming chat does, instead of `500 "[object Object]"`, and retries once with a smaller context after running out of memory, as streaming chat already did (#67). The retry happens at most once per request. Other callers of the internal JSON helper (the web-search planner, benchmarks, the OpenVINO worker) also get the engine's message. Engine messages sent to clients have local paths removed.

### Reliability (Step 9.7, #35)
* **One error model for the API** (`scripts/server/errors.cjs`). Error responses keep `{ ok: false, error }` and any route-specific fields, and add a machine-readable `code`. Statuses follow the cause: 400 invalid request, 404 missing item, 409 wrong state, 503 engine not installed, 500 server or engine failure. See `docs/runtime/API_ERRORS.md`.
* A request that triggers an unexpected error in a route is answered with a generic `500 INTERNAL_ERROR`, and the server keeps running. Wrongly typed request fields get `400 INVALID_REQUEST`. JSON bodies that aren't objects (`null`, arrays, numbers, strings) get `400` instead of no answer.
* Error messages never include stack traces or internal Node.js text. Absolute paths are shortened (studio-relative, `~` for the home folder).
### Architecture (Step 9.8, done: #36, #37, #40, #46, #56, #59, #60, #63, #65, #70)
* The server's request handling is split into a pipeline (`scripts/server/http/pipeline.cjs`), a router (`http/router.cjs`) and route modules, starting with the read-only system routes (`routes/system.cjs`). Behaviour, API responses and the interface are unchanged. Plan: `docs/roadmap/STEP9_8_MODULES.md`.
* Text-to-speech moves into `services/tts-engine.cjs` (Kokoro state, models, synthesis, outputs) and `routes/tts.cjs` (its 11 routes, including the `/tts-outputs/` audio files), unchanged (Step 9.8b, #37).
* Speech recognition moves into `services/speech-engine.cjs` (Whisper catalog, CPU/GPU backend discovery, state, the serialized job queue, transcription, translation and saved transcripts) and `routes/speech.cjs` (its 10 routes), unchanged (Step 9.8c, #40). Real multilingual translation is not yet verified: CI uses an English-only model, so it only proves that translation requests are handled.
* Web search moves into `services/web-search.cjs` (query planning, the last-message fallback, adding results to chat) and `routes/search.cjs` (its 2 routes), unchanged (Step 9.8d, #46). Searching, page fetching and caching stay in `scripts/search/`, behind the outbound guard. The trust boundary for web content is documented in `docs/security/WEB_CONTENT_TRUST.md`, with an `onUntrustedContent` integration point (unchanged results by default). USAP is not claimed to be prompt-injection-safe.
* Hardware detection and telemetry move into `services/hardware.cjs` (CPU, GPU, NPU and memory detection, the VRAM and macOS RAM polling, `/api/hardware-specs` and `/api/telemetry` reports), unchanged (Step 9.8e). The 26 functions are moved byte for byte and keep their names in `serve.cjs`. Detection order, once-per-run caching and the 5-second polling (2 timers, 3 on macOS) are the same; the timers are now started explicitly by `start()` at the same point of start-up and can be stopped. New: a read-only memory `budget` (total/free RAM and VRAM) for the future resource scheduler; nothing reads it yet. GPU and NPU acceleration remain unverified.
* Model management and downloads move into `services/model-store.cjs` (model folders, linked models, imports), `services/downloads.cjs` (the download slot and status, verified downloads, cancel, OpenVINO and image-engine downloads) and `routes/models.cjs` (17 routes), unchanged (Step 9.8f). The code was moved by a script and checked against the previous version; only server state is now read through getters. A comparison of 36 requests against the old and new server gave identical responses and files. Notes: `docs/roadmap/STEP9_8F_MODELS.md`.
* Image generation moves into `services/image-engine.cjs` (engine state, backend choice and probes, starting and stopping stable-diffusion.cpp under the engine supervisor, the OpenVINO NPU worker, Core ML, the `/v1` and `/sdapi` proxy, generation progress, saved outputs) and `routes/image.cjs` (10 routes), unchanged (Step 9.8g, #65). The code was moved by a script and checked against the previous version; engine state is read through getters (and set by the routes only where it was before). A comparison of 29 requests against the old and new server gave identical responses and files. Notes: `docs/roadmap/STEP9_8G_IMAGE.md`.
* The text engine, chat and saved conversations move into `services/llm-engine.cjs` (llama.cpp backends and probes, model settings and benchmarks, start, readiness, stop, and the Step 9.6 supervision and bounded restart), `services/chat.cjs` (chat requests, streaming, the out-of-memory retry, disconnect handling), `services/conversations.cjs` (the chat history folder) and `routes/llm.cjs` (13 routes), unchanged (Step 9.8h, #70). The code was moved by a script and checked against the previous version; engine state is read through getters (and only `llmError` is set by a route, as before). A comparison of 60 requests against the old and new server, with streams compared byte for byte, gave identical responses, streams and files. Notes: `docs/roadmap/STEP9_8H_CHAT.md`.
* **Bounded chat queue** (Step 9.9c, **off by default**): with `USAP_CHAT_QUEUE=on` (or `"chatQueue": "on"` in `app/config/scheduler.json`), one chat runs and at most 4 wait, first in, first out; more get `429 QUEUE_FULL` with `Retry-After`, waiting requests that disconnect leave at once, and none waits longer than 10 minutes (`503 QUEUE_TIMEOUT`). With it off, chat behaves exactly as before.
* New read-only route `GET /api/resources` (Step 9.9b, additive, behind sign-in): memory with known/unknown flags, CPU cores, the kind of heavy model loaded, and running and waiting work per engine. It observes only: nothing is limited, refused, queued differently or unloaded. `USAP_SCHEDULER=off` (or `app/config/scheduler.json`) removes the route. Notes: `docs/roadmap/STEP9_9_SCHEDULING.md`.
* New read-only route `GET /api/model-inspect?type=…&filename=…` (Step 9.8f, additive): a model's format, quantization (from the header, the tensors or the file name), architecture, context length, engine, size and a rough memory estimate, read from its header with bounded reads (`scripts/server/model-metadata.cjs`). It loads nothing and returns no paths; model selection and loading are unchanged. Model formats and quantization per engine are documented in `docs/runtime/QUANTIZED_MODELS.md`.
* Downloaded model archives (Core ML `.zip`) are checked before they are unpacked: only plain relative files and folders, no duplicate or conflicting names, within entry, file-size, total-size and expansion limits, and only if the drive has room. They are unpacked without a shell into a hidden staging folder, checked again, and moved into place as one transaction, so the installed model stays as it was if anything fails. An archive that fails the checks is refused and deleted, and the download status explains why (`scripts/server/archive-guard.cjs`, Step 9.8f).
### Compatibility
* **Ten error paths changed status** from 500 to 400, 404, 409 or 503 (Step 9.7; table in `docs/runtime/API_ERRORS.md`). Shapes and messages are unchanged, and the interface is unaffected. Scripts that checked for `500` on these paths should check `ok: false` or the new `code`.
* Additive API fields (Step 9.6): `GET /api/llm/status` → `engine` (state, restarts, last exit); `GET /api/diagnostics` → `engines`; chat `409` responses gain a `code` (`ENGINE_NOT_READY`, `ENGINE_STARTING`, `ENGINE_RESTARTING`, `ENGINE_CRASHED`); a cancelled load answers `409` with `code: "ENGINE_START_CANCELLED"`. Existing fields and messages are unchanged.
* **Download status** (`GET /api/download-progress`) gains two additive fields, `integrity` (`verified`, `source-checksum` or `unverified`) and `sha256`. Existing fields are unchanged. Failed downloads now delete their partial file, so the "Delete and retry" hint became "Retry the download".
* A download whose pinned digest doesn't match is refused. Setup stops with an integrity error instead of installing the file.
* **Model downloads from private-network hosts** (e.g. a NAS mirror) are now refused by default. Set `USAP_ALLOW_LAN_DOWNLOADS=1` to allow them. Loopback, cloud-metadata addresses and this machine's own network addresses are always refused (Step 9.3).
* **Browser-based third-party tools** on another origin that called the studio API (e.g. `/v1/*`) are now refused. To allow one, set `UAIS_ALLOWED_ORIGINS=https://tool.example` (comma-separated); only those origins receive CORS headers.
* If you reach a loopback-bound server through a custom hostname, add it with `UAIS_ALLOWED_HOSTS`.
* Non-browser clients (curl, scripts, SDKs), which send no `Origin`, are unaffected. LAN mode (`UAIS_HOST=0.0.0.0`) still works for same-origin use, now with sign-in for other devices (Step 9.5). The default local-only mode has no sign-in, as before.
* **Scripts posting JSON** must send `Content-Type: application/json` (e.g. `curl -H 'Content-Type: application/json' -d '{...}'`). Plain `curl -d` sends a form type and now gets `415` (S-9).
* **Scripts using a network-shared studio** need `Authorization: Bearer <token>`. `GET /api/auth/status`, `POST /api/auth/login` and `POST /api/auth/logout` are new, additive routes.
### Fixes
* Chat: a finished or failed reply is no longer overwritten by a late streaming update. An error message stays visible, and a finished reply no longer shows "Thinking..." (#6).
* Accessibility: the image-size control's accessible name now starts with its visible label (WCAG 2.5.3) (#7).
* Mobile (≤640 px): the sidebar is an overlay drawer that starts closed and closes on navigation, instead of squeezing the content. Desktop is unchanged (#8).
### Platform support
* macOS Intel: first-time setup no longer fails (#5). Image generation is now installed on Intel Macs when setup verifies an x86_64 build of the engine (#9).
* macOS: a **CPU** image backend is offered next to Metal; it's the default on Intel Macs (#9).
* Image generation never runs more threads than the machine has logical CPUs. This was a ~4–5× slowdown on 4-core Macs (#9).
* Verified with real models in CI: chat, speech-to-text, text-to-speech and image generation on the CPU on Windows x64, Linux x64, macOS arm64 and macOS Intel. GPU backends remain unverified (#9).
