# Changelog (usap)

## Unreleased
### Security
* JSON routes now refuse a request whose declared `Content-Length` is over the 64 MB JSON limit before reading its body, as the sign-in route already does, instead of reading up to the limit first. The answer is unchanged: `413`, code `BODY_TOO_LARGE`, the same message, and the connection is closed as for other refusals. Chunked bodies, which declare no length, keep the streamed limit, and accepted requests are unchanged.
* The local server now refuses requests that carry a foreign `Origin`, and (when bound to loopback) a non-loopback `Host`. Wildcard CORS headers are removed. The built-in UI is same-origin and is unaffected.
* Static file serving is confined to `app/dist/`.
* Outbound requests (web search, page fetching, model and engine downloads, Hugging Face lookups) can only reach public internet addresses. Each redirect is validated and the number of redirects is limited. The address checked is the address connected to. Search and normal downloads are unaffected (Step 9.3).
* Downloads are verified (Step 9.4). Engines, the portable Node.js and catalog models must match SHA-256 digests and sizes pinned in `scripts/config/download-digests.txt`; Node.js digests come from its GPG-signed checksum list. Other downloads are labelled `source-checksum` (transfer integrity only) or `unverified`. Files stream to a temporary file and replace the old one atomically only after verification, so a failed, interrupted or tampered download keeps the last-known-good file. Engine installs are staged, checked for the right CPU architecture and swapped in whole. Interrupted transfers are retried from the start, never resumed. See `docs/security/DOWNLOAD_INTEGRITY.md`.
* The in-app model download no longer builds a shell command for unzipping (S-8).
* **Sign-in for network sharing** (Step 9.5, S-7, #25). When the server listens beyond loopback (`UAIS_HOST`), every request from another device needs the access token, either through a server-rendered sign-in page (an `HttpOnly`, `SameSite=Strict` session cookie) or as `Authorization: Bearer`. The token is random (256 bits) and kept in `app/config/lan-access-token`; it is never logged or accepted in a URL. `node scripts/server/lan-auth.cjs rotate` signs everyone out, and `revoke` refuses all network access; both apply without a restart. Failed attempts are rate limited per client. The studio no longer forwards cookies or `Authorization` to its local image engine. The token file is restricted to the current user (mode 0600, or a Windows ACL without inherited, `Users` or `Everyone` entries), with a startup warning on drives without permissions (FAT/exFAT). Requests carrying proxy headers never get the local exemption, and throttling ignores forwarding headers. See `docs/security/LAN_ACCESS.md`.
* **Web context hardening (#42).** Text from web pages enters chat as quoted, size-capped data between per-request markers that a page can't predict. Chat-template control tokens (ChatML, Llama 3, Gemma, Mistral) are removed from it, so a page can't open a new system or assistant turn. Citations `[n]` and the UI's source list are unchanged. This reduces, but doesn't remove, the risk that a model follows instructions written in a page.
* **History marking (P3, off by default; owner approval needed to turn it on).** With `historyWeb` on (`app/config/prompt-boundary.json` `{ "historyWeb": "on" }`, or `USAP_PROMPT_HISTORY_WEB=on`, read per request), earlier assistant answers are sent to the model with chat-template control tokens removed, and answers that cited web sources also have marker brackets defused. Roles, order, other text (code included) and saved conversation files don't change. It doesn't remove plain-language instructions an answer may repeat.
* **Document records (P4-1, off by default; owner approval needed to turn it on).** `POST /api/llm/chat` accepts structured `attachments: [{ type: "document", name, text }]` on user messages. The server validates them (user messages only, at most 8 per message and 64 per request, only `type`/`name`/`text`, one-line names up to 200 characters, string text; otherwise `400 INVALID_ATTACHMENTS`) and caps document text at 120,000 characters per message and 240,000 per request with a visible note. A top-level `attachments` field is refused. With `documents` off (default), records become the chat screen's current inline text, byte for byte. With `documents: "mark"` (`app/config/prompt-boundary.json` or `USAP_PROMPT_DOCUMENTS=mark`, read per request), each document is sent between per-request random markers, quoted, with chat-template control tokens and marker brackets neutralized, and document text is kept out of web-search queries. `[Attached File: …]` text in a message is never treated as a document. Requests without records, the chat screen and saved conversations are unchanged. It doesn't stop plain-language instructions in a document.
* Web text now also has DeepSeek full-width tokens, Mistral control tokens (`[SYSTEM_PROMPT]`, `[AVAILABLE_TOOLS]`, `[TOOL_CALLS]`, `[TOOL_RESULTS]`, `[TOOL_CONTENT]`) and Qwen/Hermes `<tool_call>`/`<tool_response>` tags removed, in addition to the #42 families. Ordinary text that only resembles them is kept. Found by the P1 adversarial tests.
* **Web search query privacy (#43).** The automatic query planner now sees only the user's own last 3 messages, never assistant answers (which can repeat untrusted web content) or system prompts. A planned query that copies words from elsewhere in the conversation is refused before it reaches the search provider, and the latest user message is searched instead. The refused query is not logged. Compatibility: a follow-up that refers only to something the assistant said ("what does it cost?") is searched with the user's message as typed.
* `GET /api/web-search/config` reports `cachePath` relative to the studio folder (`app/cache/search`, or `~/…` outside it) instead of the absolute host path (#44). Same field, same type.
* **No absolute host paths in status responses (#52).** `GET /api/health`, `/api/diagnostics`, `/api/backend-options`, `/api/llm/status`, `/api/llm/backends`, `/api/llm/stats`, `/api/speech/status` and `/api/tts/status` now return paths inside the studio folder as studio-relative (`app/…`, the folder itself as `.`) and paths in the home folder as `~/…`, for every client including localhost. This covers engine, runtime and interpreter (`python`) paths, and paths quoted inside status messages (`error`, `reason`, `hint`). Values in `settings` are left as they are. System locations (e.g. `/usr/bin`) are unchanged. Field names and types are unchanged, the interface doesn't display these fields, and the server still uses absolute paths internally. Relative values resolve against the studio folder, so local troubleshooting keeps the same information without the user name.
* **Web search snippets are back (#45).** The result parser now reads each result on its own, so snippets are kept on the real results page. They were dropped whenever other markup sat between title and snippet. Order, URLs, de-duplication and limits are unchanged. Sponsored results are still included; see #50.
* **Sponsored search results are skipped (#50).** Results marked as ads on the results page (`result--ad`, an ad badge) and links that go through an ad-click redirect (`duckduckgo.com/y.js`, `bing.com/aclick`, `googleadservices.com/pagead/aclk`, `doubleclick.net`) are no longer used as sources, so the studio never opens them (which could count as an ad click) and their text doesn't reach the model. The result limit counts real results only, so a search still returns up to the same number of sources. Unmarked ads can still appear.
* JSON API routes require `Content-Type: application/json` (S-9). Other declared types and untyped bodies get `415`; a `POST` without a body still works.
* Requests the server answers without reading their body now end with the answer. This covers refused Host, Origin and sign-in checks, a wrong content type, a body over its size limit, and an unknown endpoint. The server closes the connection after a short grace period instead of reading the rest of the body, and the answer still reaches the client. Requests with no body or a small, fully sent body keep their connection as before; accepted requests are unchanged.
* A connection whose request was refused before its body was read now stays stopped during its short grace period, and a fallback check closes one that still reads anyway, normally well before its grace period ends. Previously, Node's own handling of the unread body could start reading the socket again right after the answer, so a client that kept sending was read until the grace period ended. The answer, the grace period and the close are unchanged.
### Reliability
* **Image engine port after a replacement (#170; only with `engineSlot` on, which is off by default).** A replacement image engine now chooses its port only after every earlier image engine's exit is confirmed. When the port is busy and was the previous engine's, it waits for its release (at most 5 s, polling every 150 ms), then uses the existing backup range 28088–28120 with each port verified free. A port held by another program is not waited for. A stop request ends the wait at once with `409 ENGINE_START_CANCELLED`. A start that still fails to bind is reported like any load failure, without retries. With `engineSlot` off nothing changes. The text engine already worked this way. Tests: `image-port.test.cjs` and the "#170" tests in `engine-slot.test.cjs` (a fake mode keeps the old port busy after the engine's exit; a test-only preload records the server's port checks, so the tests measure the bounded wait from the server's own checks). Details in [STEP9_9F_ENGINE_LIFECYCLE.md](docs/roadmap/STEP9_9F_ENGINE_LIFECYCLE.md) §13.6.
* **Image engine exits are classified (#120 part A).** The studio now tells a stop it asked for from an image engine that went away on its own. An engine that exits by itself after it was ready, with exit code 0 or a `SIGTERM`/`SIGKILL` the studio did not send, is now reported in `/api/backend-status` `error` instead of disappearing silently; one that exits that way during start-up is reported as a start-up failure. A requested stop never leaves an error: on Windows it ends with exit code 1 (the guard's `taskkill`), which used to show a false "exited with code 1". Existing messages for non-zero codes and signals such as `SIGABRT` are unchanged. Also fixed: an engine asked to stop that still answered while stopping (for example a stop right after it became ready) could be marked ready again, leaving a phantom "loaded" state that refused every other model until a restart. No restart, retry, timing or API change; `engineSlot` stays off by default.
* **Bounded image-generation queue (Step 9.9f-3, off by default; owner approval needed to turn it on).** Setting `imageQueue` (`USAP_IMAGE_QUEUE` or `app/config/scheduler.json`) turns it on only together with `engineSlot`; otherwise it stays off and the server logs why, and `USAP_SCHEDULER=off` turns it off. When on, the four generation routes the studio forwards run one at a time with at most 2 waiting (`429 QUEUE_FULL`), at most 10 minutes of waiting (`503 QUEUE_TIMEOUT`), refusal before the body is read while the model isn't loaded (`503 ENGINE_NOT_READY`) or over 64 MB (`413`), waiting bodies held in memory within 128 MB in total, and upload deadlines of 30 s idle and 120 s total (`408`). A client that leaves while waiting never reaches the engine; a running generation keeps its place until the engine has finished (it can't be cancelled). Stop and restart refuse waiting requests; restart is refused while a queued generation runs. Answers add a `detail` beginning "Generation failed:" for the unchanged WebUI. Inactive with the Core ML backend. Off (the default): unchanged. See `docs/roadmap/STEP9_9F_IMAGE_QUEUE.md` §13.
* **Startup stale-file report (stale-file cleanup stage R1, off by default; owner approval needed to turn it on).** Setting `staleFileReport` (`USAP_STALE_FILE_REPORT=report` or `app/config/scheduler.json`; `USAP_SCHEDULER=off` turns it off). On: once after the server listens, it counts legacy whisper temporaries (`transcriptions/.speech-*`) and old-format transcription-queue uploads (`cache/speech-uploads/`) that a hard stop may have left, and reports only counts, bytes, age buckets and errors in `/api/diagnostics` `staleFiles`. It never deletes, moves, writes or creates a file, names no file, does not follow links, reads only inside the data folder and stops at 10 000 entries or about 500 ms per folder. Off (default): nothing is read and `/api/diagnostics` is unchanged. No ownership is determined; deletion is not implemented. Design: `docs/roadmap/STEP9_9F_WHISPER_QUEUE.md` §7.1.
* Connection statistics (observe only): `/api/diagnostics` now reports `connections`, aggregate counts of the HTTP server's TCP connections from acceptance. It covers open, peak, accepted and closed connections, loopback (`local`) versus other (`lan`) peers, connections that closed without a complete request, and fixed time buckets for connection lifetime and time to the first request. It also reports refused connections in their grace period (`refusals`). It never refuses or delays a connection, does not depend on `USAP_SCHEDULER`, and stores no address, port or request data.
* **Bounded transcription queue (Step 9.9f-3, off by default; owner approval needed to turn it on).** Setting `transcriptionQueue` (`USAP_TRANSCRIPTION_QUEUE` or `app/config/scheduler.json`; `on`/`off`; `USAP_SCHEDULER=off` forces it off), with bounded, validated limits: waiting jobs (default 4), longest wait (10 minutes), upload storage budget (2 GiB), upload inactivity (30 s) and total upload time (240 s). Invalid values are ignored and logged. Off (default): `/api/speech/transcribe` and `/api/speech/stop` are the handlers from before. On: admission happens at arrival, before the body is read: `413 UPLOAD_TOO_LARGE` over 1 GiB, `429 QUEUE_FULL` with `Retry-After`, `507 INSUFFICIENT_STORAGE` when the storage budget or free disk space can't hold it, then a first-come, first-served position. The raw WAV body streams to a private `cache/speech-uploads` folder with backpressure, so server memory no longer grows with waiting uploads. The byte count is enforced, not `Content-Length`. A stalled or too-slow upload gets `408 UPLOAD_TIMEOUT`, and a job that waits too long gets `503 QUEUE_TIMEOUT`. Each request has one byte ceiling (1 GiB) and one deadline (240 s from arrival) covering both the upload and any discarding of its body after a refusal, so a refusal never extends either. A client that leaves while uploading or waiting never reaches Whisper and nothing is saved. A running transcription finishes as before and keeps its turn and file until whisper-cli exits. `/api/speech/stop` refuses waiting jobs with `409 ENGINE_NOT_READY`. Every file, storage reservation and turn is released exactly once, and this instance's files are deleted at exit. Success and error bodies are unchanged; the Whisper logical-CPU cap still applies. `GET /api/resources` gains `engines.speech.queue`, `limits.transcriptionQueue` and `transcriptionQueue` (counts and bytes only) when on. Design: `docs/roadmap/STEP9_9F_WHISPER_QUEUE.md`.
* **Bounded voice queue (Step 9.9f-3, off by default; owner approval needed to turn it on).** Setting `voiceQueue` (`USAP_VOICE_QUEUE` or `app/config/scheduler.json`; `on`/`off`, invalid values ignored and logged; `USAP_SCHEDULER=off` forces it off), and `voiceQueueMaxWaitMs` (`USAP_VOICE_QUEUE_MAX_WAIT_MS`, 1 s to 1 h, default 10 minutes). Off (default): `/api/tts/speak` and `/api/tts/stop` are the handlers from before (an unbounded wait; a waiting request whose client left still runs and is saved). On: one synthesis runs, at most 4 wait, first in first out; a full queue answers `429 { ok:false, code:"QUEUE_FULL", error }` with `Retry-After`; a request that waits longer than the limit gets `503 QUEUE_TIMEOUT`; a request whose client disconnects while waiting leaves the queue and never reaches Kokoro; a running job is not cancelled when its client leaves (its worker finishes, its output is saved as before) and the next job starts only after it; `/api/tts/stop` refuses the jobs still waiting with `409 ENGINE_NOT_READY`; every turn is released exactly once (success, error, worker crash, disconnect). Success and error bodies are unchanged. `GET /api/resources` gains `engines.voice.queue`, `limits.voiceQueue` and `voiceQueue` (counts only) when on. New `services/job-queue.cjs`; the chat queue is unchanged. Design: `docs/roadmap/STEP9_9F_WORKLOAD_QUEUES.md` §11.
* **One heavy model load at a time across text and image (issue #105, off by default; owner approval needed to turn it on).** Setting `engineSlot` (`USAP_ENGINE_SLOT` or `app/config/scheduler.json`; `on`/`off`, invalid values ignored and logged; `USAP_SCHEDULER=off` forces it off). Off (default): the previous code paths, including the known race (a text and an image load at the same moment can both succeed, two image loads can start two engines, a stop doesn't cancel an image load in progress). On: a text or image load claims one shared heavy-engine slot synchronously, before its first wait, inside its own engine's lifecycle chain (the existing text chain; a new image chain for `/api/restart-backend` and `/api/stop-backend`). The other kind gets `409 MODEL_ALREADY_ACTIVE` at once, with the existing message and `activeRuntime` plus an additive `phase` (`loading`, `loaded`, `restart-pending`, `unloading`); a text load while an image model is loaded now answers that `409` instead of `500 ENGINE_START_FAILED`. Neither engine stops the other any more. `/api/stop-backend` cancels an image load in progress or waiting (`409 ENGINE_START_CANCELLED` for that load) and answers after the exit. Image stops wait for the process exit (SIGTERM, then SIGKILL) instead of a fixed 2 s. The slot is released only after every engine process of its owner is seen to exit and, for supervised engines, its engine PID is gone; an engine that doesn't exit after SIGKILL keeps the slot and is reported (`503 ENGINE_EXIT_UNCONFIRMED` on stop and on later loads, `unconfirmedExits` in `/api/resources`). Each load has an epoch; callbacks from older processes can't change the slot or mark a new engine ready. Crash auto-restart, the out-of-memory retry, profile fallbacks and benchmarks keep their behaviour inside the text chain; an image load while a crashed text engine waits for its automatic restart cancels that restart through the text chain. Deleting the loaded text model stops it through the text chain. `GET /api/resources` gains `engineSlot` and `limits.engineSlot` only when on (fixed words and numbers only). Inference is never queued by it. Design: `docs/roadmap/STEP9_9F_ENGINE_LIFECYCLE.md`.
* **Memory-aware text-model load admission (Step 9.9f-2, off by default; owner approval needed to turn it on).** Setting `memoryAdmission` (`USAP_MEMORY_ADMISSION` or `app/config/scheduler.json`; invalid values ignored and logged): `off` (default) is the previous code path; `observe` records what would have been refused; `enforce` refuses a text-model load with `409 { code: "MEMORY_INSUFFICIENT", admission: { …, overridable: false } }`. `USAP_SCHEDULER=off` or `memoryCheck: off` force it off. Each load attempt is decided right before llama-server would start, after the previous engines were stopped, from the Step 9.9d assessment alone. A refusal needs the verdict `may-not-fit` and all of:
  * system RAM only (no GPU offload);
  * every earlier engine process seen to exit;
  * a fresh Linux `MemAvailable` reading (Windows and macOS readings aren't validated, so they only record);
  * a plausible reading;
  * no other heavy workload;
  * no Linux cgroup memory limit;
  * files at least max(1 GiB, 10 %) larger than available;
  * memory mapping off.

  Anything missing, stale, approximate, contradictory or unreadable counts as not established. A refused attempt starts nothing, tries no other profile or backend, and leaves the engine settings as they were. Automatic restarts, the out-of-memory retry, the safer-profile fallback and the model restore after a benchmark are assessed but never refused. Admission errors let the load continue. `memoryOverride` is ignored in every mode (there is no request override). `GET /api/resources` gains `memoryAdmission` and `limits.memoryAdmission` only when not off, and the memory check result gains an `admission` object. Design: `docs/roadmap/STEP9_9F_MEMORY_ADMISSION.md`.
* **Chat-engine timeouts and cleanup (Step 9.9f-1, off by default; owner approval needed to turn it on).** Setting `chatTimeouts` (`USAP_CHAT_TIMEOUTS` or `app/config/scheduler.json`): `off` (default) is the previous code path exactly; `observe` only records what would have timed out (`GET /api/resources` → `chatTimeouts.wouldHaveTimedOut`); `on` enforces. Streaming: 600 s from the request to the engine's first body chunk (the status line doesn't count), then 120 s between body chunks (SSE keep-alive comments don't count); before headers `504 { code: "ENGINE_TIMEOUT", phase }`, after them one `data: {"error":{…,"code":"ENGINE_TIMEOUT"}}` event and no `[DONE]` (the original WebUI shows it as an error). Non-streaming keeps its 300 s total (`504 … phase: "total"` when on; the legacy answer when off or observe), and in on mode a disconnected client's engine request is now aborted. Limits: whole seconds, 30–3600 and 10–600; invalid values are ignored and logged, never clamped. No retry and no engine restart after a timeout; the out-of-memory retry gets one fresh deadline. An aborted request's engine work counts as unknown until two `/metrics` readings of the same engine process, at least 3 s apart and taken after the abort, show nothing processing or deferred with unchanged decode counters. Until then no new chat is sent (the chat queue's slot stays owned). If that isn't confirmed within 120 s, chats get `503 ENGINE_UNRESPONSIVE` with `Retry-After: 30` until the engine is idle again or a new engine process starts. `GET /api/resources` gains `chatTimeouts` and `limits.runningTimeouts` only when not off. `USAP_SCHEDULER=off` forces it off. Design and evidence: `docs/roadmap/STEP9_9F_TIMEOUTS.md`.
* **Whisper threads never exceed the logical CPUs (on by default).** Each transcription passes whisper.cpp `min(requested, logical CPUs)` threads (`os.cpus().length`; an unknown, zero or invalid count changes nothing). A request at or below the CPU count is unchanged and no count is ever raised. It runs before the optional Step 9.9e budget. Saved speech settings keep the user's value; only that job's `-t` changes. `GET /api/resources` gains one additive `whisperThreadCap` object (requested and used counts, numbers only); the transcription response and `limits` are unchanged. The text and image engines, Kokoro and the macOS Intel image cap are untouched; no engine restarts. Rollback: `USAP_WHISPER_THREAD_CAP=off`, `"whisperThreadCap": "off"` in `app/config/scheduler.json`, or `USAP_SCHEDULER=off` restore the previous behaviour exactly. Measured on 3–4-vCPU CI runners only (STEP9_9E_THREADS.md §8): not a promised speed-up elsewhere.
* **Transcription thread budget (Step 9.9e, whisper only, off by default; owner approval needed to turn it on).** With `USAP_THREADS=on` (or `"threads": "on"` in `app/config/scheduler.json`), a transcription that starts while a chat is running, an image is generating or a voice job is running gets `max(1, min(requested, 2, logical CPUs − 1))` whisper.cpp threads instead of the requested count, which reduces CPU oversubscription. Alone, the requested count is used as before. The text and image engines keep their thread counts and are never restarted, Kokoro is unchanged, and nothing is refused or delayed. Busy is read from server state, never from the request; anything unknown keeps the requested count. `GET /api/resources` shows `limits.threads` and, when on, the last decision. Off (the default, or `USAP_SCHEDULER=off`) is the previous behaviour exactly. The image proxy now counts generation requests in flight (read-only).
* **Warn-only memory check before a model loads (Step 9.9d).** Just before the text engine (including automatic restarts) or the image engine starts with a model, the studio compares what the model is estimated to need (measured file sizes, plus for text models the KV cache at the chosen context from the GGUF header and a 256 MiB allowance) with the memory the system reports as available. The result is `likely-fits`, `tight`, `may-not-fit` or `unknown`, with measured values and estimates labelled separately. It appears as an additive `memoryCheck` field in the `POST /api/llm/start` and `POST /api/restart-backend` responses, under `memory.checks` in `GET /api/resources` (`limits.memoryCheck: "warn"`), and as one `[memory]` log line. It is advisory only: no load or chat is refused, delayed or changed, and no setting, queue decision or thread count changes. Unknown or implausible memory readings, missing model metadata, discrete GPU offload and image working memory give `unknown`, never `likely-fits`. Results contain no paths, file or model names. `USAP_MEMORY_CHECK=off` (or `"memoryCheck": "off"` in `app/config/scheduler.json`, or `USAP_SCHEDULER=off`) restores the previous responses exactly. No UI change.
* **Cut-off engine error responses are answered (#90).** When the text engine answered a streaming chat with an error status and then lost the connection before the error body was complete (engine crash, reset), the client never got an answer, and with the chat queue on its slot stayed held. The chat now answers `500 ENGINE_CONNECTION_ERROR` with the generic message (the partial engine text is never forwarded), exactly once, without retrying, and the queue slot is released. A complete engine error response is answered as before. An engine connection that stays open without sending anything is a different case and is not covered: it needs a timeout for a running request (Step 9.9f).
* **Chat engine connections (found by the real-model chat-queue checks).** A streaming chat that started right after another one could reuse a kept-alive connection that llama-server had just closed, and failed with `500 socket hang up`; it is now sent once more on a new connection, only when the connection had carried an earlier request, failed within 2 s with nothing back from the engine, nothing had been sent to the client and the client is still there (never more than once, and web search doesn't run again). Other engine connection errors answer `500 ENGINE_CONNECTION_ERROR` with a generic message instead of Node's, which could name the engine's local address. A chat that reaches an engine that has just stopped or crashed now answers `409 ENGINE_NOT_READY` instead of a raw `500` naming the engine's local address. Other errors and all successful responses are unchanged.
* **Engine supervision** (Step 9.6, #29). Every chat, image, speech and voice engine runs under a small guard process (`scripts/server/engine-guard.cjs`) that stops it when the studio server goes away for any reason. On Linux and macOS, a crash or `SIGKILL` used to leave the engine running with its memory and port. Windows already ended engines with the server, through Node's job object. Stops are polite first, then forced after 3 s (`USAP_ENGINE_STOP_GRACE_MS`), and wait for the port to be free. Exit codes and crash signals (e.g. Metal `SIGABRT`) still reach the server.
* A text engine that crashes after loading is restarted with the same settings after 1 s, 2 s and 4 s, at most 3 times in 10 minutes (`USAP_ENGINE_AUTO_RESTART=0` turns this off). After that, chat explains what happened. An engine that ran out of memory is never restarted (allocation errors, Windows `STATUS_NO_MEMORY`, or less free RAM than the model needs), and neither is one stopped on purpose.
* Stopping the text engine during a model load cancels it at once, instead of waiting for the load to finish, and no fallback backend is tried afterwards. `USAP_LLM_READY_TIMEOUT_MS` overrides the load timeout.
* An unexpected image-engine crash signal is reported as a clear error.
* An engine file that exists but can't be started (not executable, for example after copying to a FAT32 or exFAT drive, or a folder in its place) no longer stops the whole server (#68). The text, image and speech engines now report it as a failed start with a short explanation and no paths ("Could not start the text engine (llama.cpp) (EACCES). …"); the text engine then tries the next backend or profile as before, nothing is left running, and the next start works once the engine is repaired. The server log keeps the full details.
* Non-streaming chat (`POST /api/llm/chat` with `stream: false`) now reports the text engine's own error message and status, like streaming chat does, instead of `500 "[object Object]"`, and retries once with a smaller context after running out of memory, as streaming chat already did (#67). The retry happens at most once per request. Other callers of the internal JSON helper (the web-search planner, benchmarks, the OpenVINO worker) also get the engine's message. Engine messages sent to clients have local paths removed.

### Reliability (Step 9.7, #35)
* **One error model for the API** (`scripts/server/errors.cjs`). Error responses keep `{ ok: false, error }` and any route-specific fields, and add a machine-readable `code`. Statuses follow the cause: 400 invalid request, 404 missing item, 409 wrong state, 503 engine not installed, 500 server or engine failure. See `docs/runtime/API_ERRORS.md`.
* A request that triggers an unexpected error in a route is answered with a generic `500 INTERNAL_ERROR`, and the server keeps running. Wrongly typed request fields get `400 INVALID_REQUEST`. JSON bodies that aren't objects (`null`, arrays, numbers, strings) get `400` instead of no answer.
* Error messages never include stack traces or internal Node.js text. Absolute paths are shortened (studio-relative, `~` for the home folder).
### Roadmap
* **Step 9.9g: reliability stabilization and activation readiness** (planned, documentation only). [`docs/roadmap/STEP9_9G_STABILIZATION.md`](docs/roadmap/STEP9_9G_STABILIZATION.md) sets out seven workstreams (CI reliability; engine lifecycle and ports; cancellation and concurrency; temporary-file ownership and cleanup; security and request validation; four-platform regression validation; activation readiness review) with measurable criteria, owner-accepted thresholds (for example 98% first-attempt passes per check and runner over 50 runs, 10 consecutive green pushes to `main`, 10 consecutive qualifying four-platform native runs) and evidence rules (a relevant recurrence resets monitoring; skipped, missing or rerun results don't count; limitations need explicit acceptance), and the open issues for each. Meeting them makes a feature eligible for an activation proposal; it changes no default. Step 9.10 is unchanged.

### Compatibility
* **Ten error paths changed status** from 500 to 400, 404, 409 or 503 (Step 9.7; table in `docs/runtime/API_ERRORS.md`). Shapes and messages are unchanged, and the interface is unaffected. Scripts that checked for `500` on these paths should check `ok: false` or the new `code`.
* Additive API fields (Step 9.6): `GET /api/llm/status` → `engine` (state, restarts, last exit); `GET /api/diagnostics` → `engines`; chat `409` responses gain a `code` (`ENGINE_NOT_READY`, `ENGINE_STARTING`, `ENGINE_RESTARTING`, `ENGINE_CRASHED`); a cancelled load answers `409` with `code: "ENGINE_START_CANCELLED"`. Existing fields and messages are unchanged.
* **Download status** (`GET /api/download-progress`) gains two additive fields, `integrity` (`verified`, `source-checksum` or `unverified`) and `sha256`. Existing fields are unchanged. Failed downloads now delete their partial file, so the "Delete and retry" hint became "Retry the download".
* A download whose pinned digest doesn't match is refused. Setup stops with an integrity error instead of installing the file.
* **Model downloads from private-network hosts** (e.g. a NAS mirror) are now refused by default. Set `USAP_ALLOW_LAN_DOWNLOADS=1` to allow them. Loopback, cloud-metadata addresses and this machine's own network addresses are always refused (Step 9.3).
* **Browser-based third-party tools** on another origin that called the studio API (e.g. `/v1/*`) are now refused. To allow one, set `UAIS_ALLOWED_ORIGINS=https://tool.example` (comma-separated); only those origins receive CORS headers.
* If you reach a loopback-bound server through a custom hostname, add it with `UAIS_ALLOWED_HOSTS`.
* Non-browser clients (curl, scripts, SDKs), which send no `Origin`, are unaffected. LAN mode (`UAIS_HOST=0.0.0.0`) still works for same-origin use, now with sign-in for other devices (Step 9.5). The default local-only mode has no sign-in, as before.
* **Scripts posting JSON** must send `Content-Type: application/json` (e.g. `curl -H 'Content-Type: application/json' -d '{...}'`). Plain `curl -d` sends a form type and now gets `415` (S-9).
* **Scripts using a network-shared studio** need `Authorization: Bearer <token>`. `GET /api/auth/status`, `POST /api/auth/login` and `POST /api/auth/logout` are new, additive routes.
### Fixes
* Chat: a finished or failed reply is no longer overwritten by a late streaming update. An error message stays visible, and a finished reply no longer shows "Thinking..." (#6).
* Accessibility: the image-size control's accessible name now starts with its visible label (WCAG 2.5.3) (#7).
* Mobile (≤640 px): the sidebar is an overlay drawer that starts closed and closes on navigation, instead of squeezing the content. Desktop is unchanged (#8).
### Platform support
* macOS Intel: first-time setup no longer fails (#5). Image generation is now installed on Intel Macs when setup verifies an x86_64 build of the engine (#9).
* macOS: a **CPU** image backend is offered next to Metal; it's the default on Intel Macs (#9).
* Image generation never runs more threads than the machine has logical CPUs. This was a ~4–5× slowdown on 4-core Macs (#9).
* Verified with real models in CI: chat, speech-to-text, text-to-speech and image generation on the CPU on Windows x64, Linux x64, macOS arm64 and macOS Intel. GPU backends remain unverified (#9).

### Documentation
* Step 9.9e thread-budget design with measurements (`docs/roadmap/STEP9_9E_THREADS.md`, proposal only; nothing implemented).
* Step 9.9f first-substage design: chat-engine timeouts, cancellation and cleanup (`docs/roadmap/STEP9_9F_TIMEOUTS.md`, proposal only; nothing implemented; the planned setting is off by default).
* Step 9.9f second-substage design: memory-aware text-model load admission (`docs/roadmap/STEP9_9F_MEMORY_ADMISSION.md`, proposal only; nothing implemented; the planned `memoryAdmission` setting is off by default, refusals would need `may-not-fit` with every high-confidence condition met and a separate approval, and the first implementation has no request-based override because local callers can't yet be told apart from remote ones). It also lists the measurements needed before Step 9.9f-1 chat timeouts could be turned on by default.
* Issue #105 design: cross-engine model-load coordination (`docs/roadmap/STEP9_9F_ENGINE_LIFECYCLE.md`, proposal only; nothing implemented). Records a deterministic reproduction of the text/image load race on `cf8e5c8` and proposes an image lifecycle chain plus one synchronous heavy-engine slot with epochs and confirmed-exit release (planned `engineSlot` setting; its default is an open owner decision).
* Chat timeouts (off by default): while a cancelled request is being confirmed, the engine is probed every 2 s instead of every second. llama-server checks for a closed client connection only after a full second without results, so 1 s probes could keep it computing a cancelled prompt to the end (#133). The confirmation rule, the 120 s window and the defaults are unchanged.
* Step 9.9f-3 transcription queue design (`docs/roadmap/STEP9_9F_WHISPER_QUEUE.md`, proposal only; nothing implemented; planned `transcriptionQueue` setting, off by default). It records a measured baseline: every waiting upload is held in memory, with no bound; a waiting job whose client left still runs and is saved; there is no early 413; temporary WAVs survive a crash. It proposes FIFO by admission at arrival, streaming to a dedicated `cache/speech-uploads` folder with atomic storage reservations (507 `INSUFFICIENT_STORAGE`), upload inactivity and total deadlines, exactly-once release, and a separate stale-file sweep. All limits are provisional.
* Transcription queue (off by default): at most `limit + 2` uploads (6 by default) can be open at once, for every client alike. Past that, a request is refused at once with `429 QUEUE_FULL` and its connection is closed after the answer, without reading the upload (#131). It is reported in `/api/resources`.
* Engine supervision (#136): an engine could keep running after its guard was stopped during start-up, outside the server's process list. The guard now handles stop requests from its very start. With the engine slot on (off by default), an engine that is still running after its guard is gone is stopped through the guard's process group, and the slot is released only after its exit is seen. The server also waits longer than the guard's own grace period before forcing a stop.
* Step 9.9f-3 image-generation queue design (`docs/roadmap/STEP9_9F_IMAGE_QUEUE.md`, proposal only; nothing implemented; planned `imageQueue` setting, off by default, requires `engineSlot`). Based on CPU sd-server measurements, it proposes the following: one generation forwarded at a time; a small FIFO of waiting jobs held in the studio, so a client that leaves while waiting never reaches the engine; bounded in-memory request bodies under the one-account rule; the running place kept until the engine answers; and error bodies with a `detail` the unchanged WebUI can show. All limits are provisional.
* Step 9.9f third-substage design: voice, transcription and image-generation job queues (`docs/roadmap/STEP9_9F_WORKLOAD_QUEUES.md`, proposal only; nothing implemented; each planned queue is off by default, rolled out one at a time (voice, transcription, image), and kept separate from the engine lifecycle chains; the image queue is proposed to require `engineSlot` on).
